# Interactive landing pages

## Overview
Brand-level pages come from a **process**, not from one clever build: research real references → diverge into clearly different concepts → build each against one shared brief → verify the whole scroll path → let the client react → narrow into hybrids. Agents already animate well; what they skip is research, divergence, factual discipline and whole-path verification.

## You are the art director
The main session never builds pages itself. It writes the brief, sends **one background agent per page** (even for a single page), reviews every finished page with its own eyes (contact sheets), sends weak pages back, and shows the client only finished work. Follow `references/art-director.md` for setup, dispatch, the review checklist and learning. Every page must meet the **house taste** in `templates/taste.md` and the visual bar of the house styles in `examples/` (contact sheets of approved and rejected pages), plus this client's own reactions.
**If your prompt says you are the page builder for one page** (dispatched by an art director), you build that page yourself with the rest of this skill — don't dispatch agents.

## The loop

0. **Intake — every project, one question: the direction. Then build.** Clients prefer that you make smart assumptions and show work. At the start of every project, unless the request already names a direction ("a 3D site", "isometric"), ask exactly ONE question (AskUserQuestion, multi-select, recommended option first): **which direction(s)?** The options are the house styles in `examples/README.md`: "Surprise me — 3–4 far-apart house styles (Recommended)", "Real 3D product", "Single-product film", "Bold colour poster", "Cinematic photographic", "Path (a line the page follows)", "Flat drawn (Figma-style)", "Isometric world", "SaaS / app (product UI)" — offer the 3–4 that fit this business, each with a one-line description. Nothing else: decide concept, palette, fonts and scope yourself, take language and facts from their message, and turn any missing fact into a placeholder — never an invented fact. (If you can't even tell what the business sells, fold that into the same single question.) State the plan in 2–3 lines, build, and list every assumption in the report so the client corrects by reacting to the result.
1. **Brief first.** Fill `templates/brief-template.md`: output folder + local server URL, brand hues, fonts, audience/direction (RTL?), every section's content verbatim, the exact interaction logic (e.g. pricing maths), hard rules, and a **Client taste** list (loves / rejected) that grows every round — it always starts from the house taste in `templates/taste.md`; this client's reactions are added on top and win where they conflict. All variants read this one file.
2. **Research before designing.** When a brand, site or Mobbin link is named — or the client says "like the big international brands" (pick 2–3 fitting ones yourself) — follow `references/brand-research.md` (Mobbin queries + measuring the live site) and write `research-<brand>.md`. For a known family, start from `references/brand-styles.md`. Never build "Stripe-level" from memory.
3. **Diverge.** If the client asked for one page / one direction, build one — but pick it from 3 written concept sketches, not the first idea. Otherwise round one = 4–6 variants that are far apart: different spine (`references/concepts.md`) AND different style family (drawn / SaaS-light / SaaS-dark / photographic / editorial / playful). Offering one polished direction is the most common failure — the client's reaction to contrast is the information you need.
4. **Build in parallel — never in the main session.** One background agent per page, dispatched together with `templates/variant-dispatch.md`. Each works only in its own folder; you stay free to talk to the client.
5. **Review as art director.** Agents verify their own page (below), but that is not enough: when each reports, run `shots.mjs` on it yourself, look at the contact sheet at 1440 (and 375 for pinned stories), check it against the list in `references/art-director.md` §3, and SendMessage fixes back. Only finished pages reach the client. First time on a machine: `node scripts/doctor.mjs`.
6. **Relay reactions.** For a revision of an existing page: audit it first (invented facts, implied facts, what the client disliked), measure the complaint before and after (motion count, shapes per screen, type sizes), and log what was removed. Turn each client remark into a rule in the brief's taste list ("everything bigger", "no framed sticky header", "not like a design tool", "cleaner — one drawing per section") and SendMessage running agents instead of restarting them.
7. **Narrow.** Hybrids of what they liked (A's drawings × B's motion), then a clean spec → one final build.
8. **Full site (after the homepage is approved).** Follow `references/full-site.md`: extract the design system from the homepage, sitemap from the facts, inner pages quieter but never template (one signature moment each), shared header/footer/assets, SEO basics, and walk every page.

## Craft floor (never lowered — not for urgent, serious, small or "simple" briefs)
A correct-but-timid page is a failure; clients rank it last. Tone changes **speed, palette and restraint of motion**, never ambition:
- **One spine** from `references/concepts.md` that the whole page follows (a law firm can be "a case file opening", a clinic "one visit, hour by hour").
- **Big, confident type:** at 1440 the hero headline ≥ 88px, section headlines ≥ 56px, body ≥ 19px. Check `typeScale` in walk.mjs.
- **One visual system** that is not stock decoration: drawings, real photography, or type-as-image — used large.
- **At least one signature scroll moment** (pinned beat, draw-on, portal, stacking…) — calm pages get a slow, precise one, not none.
- Serious sectors (legal, medical, finance) look like Aesop, Stripe Press, Pentagram editorial — rich and quiet, not empty.
- **Use the canvas:** hero and section headlines span the width (or sit big and centred); one idea per screen; photos full-bleed or at least half the viewport — never a small card or arch floating in white; nav and buttons sized to match (≥ 16px text, ≥ 48px tall).
- **Design around the facts you have.** A section whose main content would be placeholders (listing cards with no listings, treatment cards with no descriptions, price tables with no prices) is redesigned: show the known part huge (the names, the one fact), and replace the rest with a single CTA ("ask us about current listings"). Placeholders are small inline tags, at most one visible per section — never whole cards or a page of dashed boxes (exceptions: each closed FAQ answer may hold its own tag; a contact section may show one for the phone/number and one for consent — or merge them into one tag). The full list lives in the HTML comment and the report.
- **Thin content** (no listings, menu, portfolio or answers yet): make the service structure itself the visual (floors of a building, stations of a path, states of one object) — never a grid waiting for content.
- walk.mjs also reports `largestVisualPctOfScreen` (largest visible image/SVG/canvas/mockup area, max over the walk) and `h1WidthPct` (width of the hero headline TEXT, not its block, as % of the viewport): a main visual under ~35% of the screen (a portrait phone mockup is the exception — judge it by height) or a hero headline under ~45% of the width usually means "small thing floating in white" — look again.
- **Luxury and "calm" still move the camera:** a product held in one framing with overlays around it was rejected as "bad" (perfume). Travel: macro → whole object → inside it → out again, the object ≥ 70% of the screen height at its hero moment.
- **Minimal is not premium:** an abstract thin line on empty dark screens with faint words was rejected as "bad" (finance). Something big and concrete must fill every screen — a drawn/isometric/photo world, an object, or giant type at full contrast.
- **Dark is fine when it is lit:** SaaS-dark and cinematic pages work when light, colour and composition change beat to beat; "gloom" means dark AND monotonous.
- **Premium, not local-template:** treat a garage, clinic or shop like a product brand (the client rejected three garage pages as "local template" / "grim poster"). Prefer the product-page treatment — one hero object, light studio or crisp drawing, a transformation — over signage clichés (hazard tape, yellow/black) and over all-dark gloom.
- **Vary the chapters:** never repeat one composition (e.g. dark photo + white word) for every service — change scale, side, camera and layout from chapter to chapter.
- "Calm / gentle / anxious audience" means slow, soft, reversible motion and shorter pins — still a designed moment, never a plain stack of text blocks.
- **The footer is the last chapter, not an afterthought** (the client: "everything is stunning and the footer is very thin"). Give it the same care as the hero: (1) a closing moment from the page's world — the 3D object settles or turns one last time, the isometric world lit at night, the drawn object parked, the path's end — with a final big CTA; (2) a giant wordmark that animates in (rises letter by letter, draws, fills) and fills the width; (3) real structure in big-enough type (≥ 16px): sitemap columns, contact (phone/WhatsApp/email/address as placeholders), hours if confirmed, socials (placeholders), newsletter if relevant, the business's one-line promise; (4) a quiet legal row (terms, privacy, accessibility, © year, disclaimers and "illustrative" notes). At least one full screen tall at 1440; on phones the columns become big tappable rows. Never just a wordmark plus a line of small links.

## Content rules (hard)
- Only facts from the brief. No invented logos, testimonials, ratings, customer counts, statistics, prices, policies, opening hours, delivery terms or feature claims. If a section needs a fact you don't have, use a clearly marked placeholder and list it in the report.
- **Implied facts count:** sensor views (thermal, lidar, measurement overlays) imply the client owns that equipment; on-screen readouts (altitude, battery, resolution, km) are invented numbers unless given. Maps of a country or region: avoid borders unless the client supplies the map. Colour and quantity imply too: a pink scoop reads as strawberry, a three-scoop cone implies you can buy one — name no flavour, add a "colours are not flavours" line, prefer non-food hues. Options side by side (instruments × format × age, services × areas) imply every combination is offered — don't pair them unless confirmed. Floor plans imply room counts, sizes and adjacency — label "illustrative plan" and list what it implies. Membership/space pickers with unknown prices: the summary says "ask us" and hands the choice to the form. SaaS numbers imply too: time gaps between detection and alert imply speed, the number of regions/pings implies coverage, chart axes imply normal performance, automatic state changes are feature claims. Demo inputs that "run" (terminals, try-it boxes) say they contacted nothing. Computed/recoloured paints shown as a product's colours are implied facts — label "computed, not a paint sample". Rentals/bookings: a route between two pick-up points implies one-way rentals; one body recoloured per class implies every class is the same car; time and price rows imply availability. Travel: a route joining several countries implies combined trips are offered (draw separate routes from home instead); a landmark photo implies the trip goes there. A photo under a place name implies that is how the place looks — label it "not a photo of <place>".
- **Implied facts, examples:** a drawn baguette implies it is sold; "open now" logic implies hours; describing a step ("we handle permits") implies scope — word process steps without implying outcomes ("paperwork is a step", not "we get your permit"). Draw generic, show logic only for confirmed data. A day missing from confirmed hours (e.g. Saturday) is shown as closed and reported; holidays stay a placeholder. Graphics that look like medical images (X-ray, scan) are labelled as a graphic effect, not a real image. Night/emergency scenes imply night or 24/7 service. When the client's own direction asks for an implied fact (e.g. "show a moisture sensor"), draw it and flag it in the report.
- **Sample values inside UI** (catalogue %, prices, SKUs) use a neutral "sample value" chip style (`[%]`, `[₪]`), distinct from the orange placeholder tag and exempt from the one-per-section count.
- **Placeholders** are small, full-opacity inline tags reading "[… awaiting <client>]" (see "Design around the facts you have"), also listed in an HTML comment at the top; the report lists them as launch blockers.
- Disabled controls are styled with colour, not opacity (opacity reads as hidden to the checks and to users).
- **Children's services / parent trust** (camps, kindergartens, schools): faceless figures; recognise the parents' key questions (ratios, supervision, safety, food) as a FAQ whose answers are placeholders — never answer them. A calendar strip's highlight position is itself a date claim — label it illustrative.
- **Subscription pickers** are shops: the uniform demo price wins over "no price", shown per delivery plus an explicit period ("per 4 weeks"). Food boxes: pictured items imply contents and season, "how many fit" implies quantity per size, add-ons inside the box imply farm produce — label all.
- Background removals, upscales and build-time composites don't count toward the image-prompt budget; report them.
- **Pickers/planners that send nothing** (trip planner, room calculator, pack builder): they may hand the selection to the form, but the summary promises nothing (no price, no availability) and says the form is not connected.
- **Lines read as charts:** a line rising to the top-right reads as growth/returns — on finance pages no net rise, horizontal tangents, no axes, plus a "not a chart" note. "Independent" invites un-given claims (objective, no commissions, no conflicts) — don't add them. Avoid outcome words ("financial security", "peace of mind", "grow").
- **Money:** labelled sample transactions/amounts in UI are fine; never balances presented as real, rates, returns, growth or time-to-goal projections; avoid "safe, protected, insured, earn, grow, interest" unless confirmed. Size sample data so the visual and the numbers agree (a jar can't look full at 6%) and report the choice. Render ₪ at the display weight before choosing a font — many Latin fonts lack it or draw it badly.
- **Quotes and premiums** (insurance, loans, finance): never show a demo quote/premium number — a skeleton bar or "shown with your quote". **App-only products:** the main action is the store link; unknown links = disabled generic store buttons (no Apple/Google badge artwork) + one tag. Exercise/feature types shown in app mockups are feature claims.
- **Client loosens a hard rule mid-build:** record it in the brief as a dated "supersedes" note and apply it; keep the facts rules.
- **Brief facts that look wrong** (e.g. renters insuring the structure): keep the brief's wording, and flag it in the report — don't silently fix or repeat it as if checked.
- **Portfolio trades** (nails, hair, tattoo, photography, architecture; boutiques whose products are designer goods): the photos ARE the work — generated images must be labelled mood/illustrative and listed as launch blockers to replace with the owner's real work; drawn or type-led directions avoid the problem entirely.
- **Licence gates** (prescription/controlled products) are not age gates: a self-declared "I have a licence" is legally weak and a public product listing may itself be prohibited advertising — build it, and flag both for the client's lawyer. Check the brand name's meanings and associations (a party, a slang term). Medical pages: every treatment statement defers to the physician, in one consistent line.
- **Age gates / blocking modals:** accessible dialog, focus inside, Escape cannot dismiss (block the key and reopen on close — Chrome ignores a dialog's blocked Esc without prior user activation), never blocks no-JS reading, 18+ confirm again at checkout; support a `#qa-skip-gate` hash so verification can run, and list it as a launch blocker to remove.
- **Forms:** no real endpoint → the form says "not connected yet" on submit, never a fake "sent"; POST only (no personal data in URLs); consent/privacy line as a placeholder.
- **Regulated sectors** (legal, medical, controlled/prescription products such as medical cannabis, wellness/fitness/prenatal, education outcomes ("fluent in X weeks"), financial/accounting, psychological, alcohol, gambling, aviation/drones): no promised outcomes, success rates or "best"; disclaimers, licence numbers, age gates (18+) and legally required warnings are placeholders for the client to approve. Pose, exercise or breathing cues drawn on yoga/fitness pages get a "not practice instructions" note. Audit symbols and metaphors too ("sharper / clearer" on an optician page reads as a vision promise; eye-chart fractions imply a measurement): two chairs facing each other read as opposing sides, a dismissal letter implies a scenario, scales imply an outcome. A cultivation or lab scene implies the business runs a production facility, so label it "illustration, not our facility". Props the client asked for (a van, a scanner) stay in but go on the implied-facts list. On finance pages, growth imagery the client asks for (a tree growing) stays a life metaphor: no rising lines or paths going up the screen.
- **Hiring / HR pages:** sample job ads and candidates show no preference by age, gender, origin or religion — and no proxies for them (photos, ages, languages, weekend/Shabbat availability, distance, years of experience). Candidates are initials on flat avatars or faceless drawn figures. In Hebrew, job ads must address all genders (slash forms "דרושים/ות", "מחפש/ת", or gender-neutral nouns). No "hire in 24 hours", "guaranteed match", match rates or AI claims; candidate-data/privacy and equal-opportunity wording are placeholders.
- **Two-sided products** (marketplaces, hiring, booking): give each side its own chapter and its own CTA, with one placeholder tag per section; whether it is one app or two is an implied fact. Pick which side leads from the brief, else lead with the paying side.
- **Brand names:** check the invented name isn't a real competitor (a common trade word like "דרושים" can be one), a political party (צומת, גשר) or an acronym that reads as one; trademark check is always a launch blocker.
- **Crypto / web3:** no APY, rewards, "earn", "passive income", price charts or live-looking tickers; whether a token exists, chains, audits, custody ("non-custodial"), "decentralized = secure" and team/legal entity are claims → placeholders; a risk-disclaimer and jurisdiction placeholder in the footer. "Connect wallet" / "Launch app" buttons claim the app exists and must never open a real wallet prompt — show them as not connected. A structured footer may carry one tag per block (contact, consent, legal). **Privacy products** (privacy coins, VPNs, encrypted apps): never "untraceable", "anonymous forever", "impossible to track", hiding from government/taxes, laundering or sanctions framing; present privacy as ordinary (curtains, a sealed envelope, covering a keypad), not as secrecy or crime — no masks, hoodies, skulls, shadows; add a "lawful use" placeholder. A technology may appear only as a neutral sample chip ("e.g. zero-knowledge proofs — sample concept").
- **Real brands:** default to a fictional brand. If the client explicitly wants the real product or brand (or it's their own client), use the name as plain text only (no logo artwork), take specs only from the maker's published pages with source URLs, and put a clear line in the footer: "Unofficial design concept — not affiliated with, endorsed by or produced by <brand>. <brand> is a trademark of its owner." No real purchase flow or store links on such a page.
- **Weapons and other restricted products:** enquiry-only (licensed/authorised buyers, age + licence + export-control placeholders), never a cart or price. Showcase form, material and light only: no people shooting, targets, combat scenes, muzzle flash or lethality/"stopping power" copy; leave out performance specs (rate of fire, range). The muzzle never points at the viewer — every turn passes through the side facing away. Exploded views show exterior modules only.
- **Agency / studio sites:** the portfolio is the proof — use the client's own case pages (named rows or big device frames with screenshots of their own work), never invented results, quotes or metrics; founders without photos get monograms or names; "Join our team" without a URL is a placeholder tag. With no brand font, choose one that serves the direction (e.g. a variable font with a width axis for kinetic type) and report it. Build one language first and note the second. Case-page images may contain third-party people and brands — crop to the work and list them. If the agency has a logo you've seen (measure the live site), echo its mark and colour rather than inventing a new one. Portfolio screenshots are ~2:1 desktop shots: show them in big browser/monitor frames, not phone frames; crop for phones at a content boundary (never mid-word) and keep RTL sites' right side. Invented UI for a service agency (code editor, design canvas, ads console) is a metaphor — label it "sample" and use a neutral stand-in client ("your-business.com"), never a ranking or result; a sequential stage reads as a process, so note "phases are illustrative". Nav items with no page yet (careers, language switch) point to contact/email or carry a tag. Sections the agency has no facts for (process, team, testimonials, results) are left out, not filled with placeholder tags. Case pages may carry result claims or extra service tags — use only what the brief confirms. When the direction forbids faces but a case image is a photo of a person, crop to the site UI or pick another image of that project, and flag it. If every image of a project shows people, use its logo plate or a UI detail.
- **Baby, infant and care products:** no health or medical claims even when the brand's own site makes them (colic, reflux, "clinically proven", "just like breastfeeding", "saves lives") — drop them; keep sourced mechanism wording ("the sensor changes colour when the liquid is too hot") with a "wording to be approved" tag; usage, safety and warning text are placeholders. No babies' faces; no fear imagery of older people (falls, pain) — calm and dignified. A clinical look must stay descriptive: section drawings, "DETAIL" frames, part numbers and data sheets imply rigour, so number them as "the page's own, not the maker's", give every spec row a source column, and show "— mm" only once per view when dimensions aren't published. For older-adult products: body ≥ 20px, buttons and tap targets ≥ 56px, 4px focus rings, big form fields and radio tiles, a text-size toggle in the header, no motion needed to understand the page. Care/safety alarms: no life-saving, response-time, "24/7", "connects to emergency services" or fall-detection claims unless confirmed, plus a "does not replace emergency services" placeholder. Client photos may themselves be fear imagery (a fall, chest pain) — don't reuse them; show the wearer faceless (a neckline, a hand). Wearer and buyer are two audiences: the hero speaks to the wearer's independence, the form asks who it's for. When the product's colour is also the alarm colour (red), use a deeper shade for buttons and keep it out of floods.
- Every agent reports **new wording** (anything not verbatim from the brief) so the client can approve it.
- **Sample content in invented product UI** (no real app shown to you): label every mockup "Sample content", keep names generic, show only states that map to brief facts (every column, badge and button is a feature claim), and list sample content separately from placeholders. Keep invented UI to what the story needs — avoid search, filters, avatars, activity logs, amounts and reports unless given; translated stage/menu names count as new wording. Unknown signup/trial URL → a button that says it isn't connected.
- Real product UI stays recognisable — restyle its frame, not its data. Inspired by a brand ≠ copying its logo, copy or UI.

## Build rules
- Prefix component classes (`term-row`, `feat-row`, `cart-scrim`) — generic names (`.row`, `.ring`, `.ghost`, `.scrim`, `.in`) collided in almost every single-file test.
- One self-contained HTML file per variant; transforms/opacity only (plus attributes of small inline SVGs — fills, `d`, dash offsets); one rAF scroll loop; never intercept the wheel. Recipes: `references/motion-recipes.md`.
- `overflow-x: clip` on every section/stage; pinned runways sized from beats with something changing every step.
- Content visible **without JS**: hide-for-reveal classes only under `html.js`; pinned stages fall back to stacked static states; header gets a background.
- `prefers-reduced-motion`: no scroll-driven pinning or parallax, everything shown (static sticky photo backdrops that captions scroll over are allowed).
- Real-time 3D (a "real 3D" direction): three.js from a pinned CDN version is the one allowed external script — follow `references/real-3d.md` (procedural models, fallback stills, performance, glass/stacking traps).
- Isometric scenes: reuse `assets/isometric-engine.js` — read `references/isometric.md` first (axes, solid fields, draw order, groups, text on faces, camera, baking the SVG for no-JS).

## Verification (mandatory, per variant)
Run `scripts/walk.mjs` — real wheel steps to the bottom **and back up**:
```
node scripts/walk.mjs <url> 1440 900 --font "<font>"
node scripts/walk.mjs <url> 375 812
node scripts/walk.mjs <url> 1440 900 --nojs
node scripts/walk.mjs <url> 1440 900 --reduce
```
Review pinned stages beat by beat with `node scripts/shots.mjs <url> <dir> --n 12` (or `--from 0.1 --to 0.4` for one runway) — it writes frames plus one contact sheet to look at. Add `--shots <dir>` to walk.mjs for evenly spaced screenshots and `--workdir <your scratch folder>` (the Chrome profile is created there and deleted).
Pass = `noHorizontalOverflow` true, `heightStable` true, `deadScrollSteps` 0 (JS runs), nothing important in `neverFullyVisible`, no console errors, only the brief's fonts, `typeScale` meets the craft floor, `pinnedStages` ≥ 1 unless the client rejected pinning or the spine is continuous (Path, Ribbons — then one chapter still gets a slow pinned moment or an equally strong scroll-linked one). With `--nojs`, a small height change from the font swap and deliberately disabled controls are expected. Also check: hero (headline, sub, CTA, trust line) inside 1440×900, every interaction works, pricing maths at every stop. Then look at ≤16 screenshots yourself — always including a phone contact sheet of every pinned runway (`shots.mjs --from/--to` at 375): checks passed an EMPTY phone board more than once — including drawing quality: every drawn object must read as that object at thumbnail size (watch for accidental faces from paired strokes, scoops that read as jellyfish).

## Hygiene
- On Windows Git Bash, arguments starting with `//` are rewritten as paths — set `MSYS_NO_PATHCONV=1` for scripts that take URLs or `//` patterns.
- `canvas-job.mjs` / `compress.mjs` are slow on 4–11 MB sources (minutes): compress large generated images first and run long jobs in the background.
- **Editing the skill's own scripts:** they run code inside template strings evaluated in the page — a quote of the wrong kind breaks them silently (typeScale comes back EVALERR). After any script edit, run it once on a published page and check the output before handing it to agents.
- Scripts, screenshots and browser profiles live in the scratch subfolder — never in the delivery folder, never outside your own folder. Never delete other agents' files or the brief.
- `scripts/cdp.mjs` deletes its Chrome profile after exit. Pass `--workdir` so profiles live in your own folder; clean up only `ilp-prof-*` folders you created — never shared temp folders other agents may be using. The orchestrator checks free disk space after a parallel round.
- Use your own headless Chrome — not the user's personal browser.
- Downloads and background commands use absolute output paths inside your own folder (`cd x && curl … &` in a background shell has written files into the project root).
- Preview: open the page as file:/// or run `node scripts/serve.mjs <site folder>` (pick a free port and confirm it serves YOUR page).
- Pixel work (flatten a studio background, key a region into a mask, recolour, cut a part into its own layer): `node scripts/canvas-job.mjs <job.js> <outDir> <images…>` at build time — file:// pages cannot read pixels back.
- Images: `node scripts/compress.mjs <in> <out.jpg> 2000 0.8` (headless Chrome, no ImageMagick needed); export 2000w + 1100w and use `srcset`. Generated photos are placeholders for the client's real ones; generated vehicles and gadgets drift toward real models — prompt for a concept design language (e.g. a light bar, no grille) and reject anything that reads as a known product; for a physical product the client hasn't shown, every generated view invents its design — generate all views from one reference image (or draw the product) so at least the page is consistent, and list the design as a launch blocker. Demo interactions ("tap a zone") must be labelled as demos so they don't read as product features. Generated images are labelled "illustrative", and what they show (a view, a dish, a room type) counts as an implied fact.
- RTL: wrap number ranges, times and phone numbers in `<bdi dir="ltr">` (or LRI/PDI) and join "עד 20:00" with a no-break space — otherwise "08:00–19:00" renders reversed.

## Red flags — stop
| Thought | Reality |
|---|---|
| "One strong concept is enough" | Round one needs contrast. Build 4–6 far-apart variants (or 1 chosen from 3 sketches when the client asked for one). |
| "It's urgent / serious, keep it simple" | Simple layout, full craft. The timid law-firm page was ranked worst of 25 tests. |
| "A clean clinic/agency/garage template is appropriate" | Clients rejected exactly that: narrow column, small type, stock photo in a card, dashed placeholder boxes everywhere. |
| "I know what Stripe looks like" | Measure it. Research files beat memory. |
| "I'll fill the FAQ/menu with plausible answers" | Invented facts. Placeholder + report. |
| "Screenshots at key points look fine" | Walk the full path down and up, plus --nojs and --reduce. |
| "Reveal animation needs content hidden" | Only under `html.js` — no-JS must show everything. |
| "Leave the QA folder next to the page" | Scratch folder only. |
